# Contributing

Thank you for your interest in contributing to Ironicl! We welcome contributions from
everyone.

This project is hosted on https://github.com/probabl-ai/ironicl.

Below are some guidelines to help you get started.

## Our values

We aspire to treat everybody equally, and value their contributions.
We are particularly seeking people from underrepresented backgrounds in Open Source Software to participate and contribute their expertise and experience.

Decisions are made based on technical merit, consensus, and roadmap priorities.

Code is not the only way to help the project. Reviewing pull requests, answering questions to help others on mailing lists or issues, organizing and teaching tutorials, working on the website, improving the documentation, are all priceless contributions.

We abide by the principles of openness, respect, and consideration of others of the Python Software Foundation: https://www.python.org/psf/codeofconduct/

## Automated contributions policy

Please refrain from submitting issues or pull requests generated by fully-automated tools. Maintainers reserve the right, at their sole discretion, to close such submissions and to block any account responsible for them.

Ideally, contributions should follow from a human-to-human discussion in the form of an issue.

## Questions, bugs, and feature requests

Questions, bugs, and feature requests can be filed in the [GitHub issue tracker](https://github.com/probabl-ai/ironicl/issues).

When filing an issue:

* Check if your issue does not already exist.
* For [new issues](https://github.com/probabl-ai/ironicl/issues/new), use [short, self-contained, correct examples](http://sscce.org/) to help us understand your issue.
* For bugs, include the Ironicl commit and the output of `ironicl platform`.

Report security vulnerabilities privately, as described in [SECURITY.md](SECURITY.md). Do not open a public issue for them.

## Pull requests

Quick start:

- Create a branch for your changes.
- Commit your changes.
- Push to your fork.
- Submit a pull request to the `main` branch.
  - Link your PR to its corresponding issue (if any).
  - You can mark your PR as draft if it is not ready to be reviewed by maintainers. You can use draft PR to get help on the code if needed.

We use the [conventional commits](https://www.conventionalcommits.org/en/v1.0.0/#summary) format for PR titles:

- In particular, commits are "sentence case", meaning that the `fix: Fix issue` title passes, while `fix: fix issue` does not.
- Generally, the description of a commit should start with a verb in the imperative voice, so that it would properly complete the sentence: `When applied, this commit will [...]`.
- Examples of correct PR titles: `docs: Update the README` or `feat: Add BF16 context storage`.
- Allowed types: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `release`, `revert`, `style`, and `test`.

Ironicl is a company-driven project. We might provide extensive help to bring PRs to be merged to meet internal deadlines. In such cases, we will warn you in the PR.

Keep changes focused and include tests for behavior changes. Run the relevant
checks below before requesting review. Run all commands from the repository root.

## Setup

Install rustup, Make, and Python 3.12 or newer. On macOS, install the Xcode Command
Line Tools; on Linux, install a C compiler and linker.

Rust commands use the version and components in `rust-toolchain.toml`. Install them
with `rustup toolchain install`. This is the tested toolchain, not a declared minimum
Rust version. Update the pin deliberately and validate both CI platforms.

For Python development, create a virtual environment and install the package:

```sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install --editable .
```

This environment does not need TabICL or PyTorch. Use a separate environment for
live upstream comparisons.

## Local checks

| Command | Scope |
|---|---|
| `make test-rust` | Rust tests with default features and with `--no-default-features`, using `Cargo.lock`. |
| `make lint-rust` | Formatting and Clippy for all feature configurations; warnings are errors. |
| `make audit` | `Cargo.lock` against the RustSec advisory database; needs `cargo install cargo-audit`. |
| `make lint-python` | Ruff pyflakes (`F`) checks for `python/ironicl` and `tools`; needs `pip install ruff` (or `uvx ruff`). |
| `make test-python` | Standalone preprocessing and exporter tests, including the frozen upstream oracle. |
| `make test-parity` | Direct comparisons with the pinned TabICL checkout; requires a separate environment. |

The Python targets use `python3` from `PATH`. Override the interpreter when needed:

```sh
make test-python PYTHON=/path/to/venv/bin/python
```

The Python targets do not install dependencies. Only `make test-parity` downloads
the released classifier checkpoint. Rust checks may download the pinned toolchain and Cargo dependencies
on first use. To fix Rust formatting, run `cargo fmt --all`; `make lint-rust` only
checks it.

### Live TabICL parity

Follow [the parity setup instructions](docs/validation.md#python-preprocessing-parity)
to install the Ironicl wheel and pinned TabICL checkout in a separate environment.
Then run:

```sh
IRONICL_TABICL_SOURCE=/path/to/tabicl/src \
  make test-parity PYTHON=/path/to/parity/bin/python
```

The suite verifies the upstream revision and imported source path. Missing
prerequisites fail rather than skip. These tests compare preprocessing, not neural
outputs or classifier predictions.

## CI coverage and limits

The Rust workflow runs `make lint-rust` and `make test-rust` on Linux x86-64 and
Apple Silicon, and `make audit` once on Linux. The Python workflow tests an
installed wheel built from the source distribution, rather than the editable
checkout used for local development. It runs standalone and live parity tests in
separate Linux/Python 3.12 environments.

Rust CI does not provision official model or oracle fixtures. The tests in
`tests/checkpoint_fixtures.rs` and `tests/gpu_build_groups.rs` are marked
`#[ignore]`, so a normal `make test-rust` reports them as *ignored*, not passed.
To run them, provide the fixtures and pass `--ignored`:

- `IRONICL_CHECKPOINT_FIXTURES`: a directory containing both official v2 checkpoints
  and the imported classifier artifact `tabicl-classifier-v2.ironicl`.
- `IRONICL_ORACLE_FIXTURES`: a directory containing `input.irinput` and
  `logits.irlogits` from the upstream exporter.

```sh
IRONICL_CHECKPOINT_FIXTURES=/path/to/checkpoints \
IRONICL_ORACLE_FIXTURES=/path/to/oracle \
  cargo test --locked -- --ignored
```

With the variables set, these tests fail loudly when a fixture is missing instead
of skipping silently.

See [the validation guide](docs/validation.md) for fixture generation and numerical
requirements. CPU-feature-gated kernel tests run automatically where the CPU feature
is present and no-op where it is not (a current harness limitation); benchmarks
marked `#[ignore]` do not run by default. Green CI is not proof of upstream model
parity or Zen 5 performance.
